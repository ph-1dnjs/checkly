# AI 브라우저 TC 실행 구현 정책안

> 상태: MVP 구현 반영 · 작성일: 2026-11-03. 이 문서는 목표 정책이다. 실제 구현된 동작과 구현하며 확정한 값(엑셀 상한, 병합·숨김 처리, AI 제공 방식, 기본 실행 한도)은 [AI TC 실행 기능 문서](04-pages/080-ai-tc/README.md)를 따른다. 팀 공유 저장과 보존 기간은 아직 미확정이며 구현하지 않았다.

## 1. 목적과 범위

사용자가 Excel TC를 가져와 선택하면 AI가 실행 중인 브라우저를 관찰하고 조작해 테스트한다. TC의 기대 결과마다 관찰 근거를 남겨 사람이 판정을 검토할 수 있게 한다. 프론트엔드 소스 분석 및 코드 기반 시나리오 생성은 이 기능의 선행 조건이 아니다.

### MVP 범위

- `.xlsx` 업로드, 시트·열 매핑 확인, TC 선택과 검토.
- 하나의 실행에서 TC를 순차적으로 처리하는 단일 Playwright Chromium 브라우저 컨텍스트와 활성 페이지. 팝업 발생은 감지하고 자동 전환을 지원하지 못하면 사용자에게 인계한다.
- AI의 화면 관찰과 제한된 브라우저 동작, 사용자 인계 및 재개, 취소.
- TC와 기대 결과별 판정, 동작 이력, 근거, 실행 환경과 오류 표시.
- 로그인된 팀 프로젝트의 웹 테스트 규칙을 따른다. Supabase 설정이 없는 개발·테스트 환경에서만 로컬 모드를 허용한다.

### MVP 제외

- 프론트 소스 분석, 코드 생성, 생성한 Playwright 코드 실행, 기존 Markdown 시나리오로의 자동 저장.
- PC Edge·Safari의 실제 브라우저 실행, 실제 iOS·Android 기기, 병렬 실행, 다중 계정 동시 제어.
- 임의 셸·파일·HTTP 요청 도구, 독립적인 API 검증, OS 전체 제어, CAPTCHA·2차 인증 자동 우회.
- 엑셀 결과 열에 원본을 덮어쓰기, Jira 등록, 결제 대행 및 SAP 등 외부 시스템 제어.

## 2. 기준 TC와 입력 해석

예시 파일 `QA_프로모션 카테고리_v1.1.xlsx`는 `BOS_시나리오`, `BOS_TC`, `플랫폼_시나리오`, `플랫폼_TC`, `결과요약`의 5개 시트를 가진다. `BOS_TC`는 73개, `플랫폼_TC`는 42개 TC다. 시트의 `TC ID`, `시나리오 ID`, `구분`, `사전 조건`, `테스트 단계`, `기대 결과`, `테스트 데이터` 열을 기본 매핑한다. 브라우저별 기존 결과·담당자·Jira·증빙 열은 참고 정보이며 테스트 지시나 현재 실행 결과로 간주하지 않는다.

1. 파일은 사용자 선택으로 읽는다. 파일 형식, 크기·시트·행·셀 길이의 상한을 적용하고 초과하면 가져오지 않고 이유를 알린다. **상한의 구체적인 수치는 구현 전 확정한다.** 매크로 실행과 외부 링크 갱신은 하지 않는다.
2. 시트와 열 매핑을 미리 보여 주고 사용자가 수정할 수 있게 한다. 필수 열은 `TC ID`, `테스트 단계`, `기대 결과`다. 사전 조건 등 선택 열이 없어도 가져오되 누락을 표시한다.
3. 원본 파일은 변경하지 않는다. 원문, 파일명, 시트명, 행 번호를 보존한다. 숫자 목록은 항목별로 나눌 수 있지만 전체 원문도 보존하고 잘못 분리한 항목을 사용자가 수정할 수 있게 한다. 하나의 기대 결과에 여러 조건이 있으면 검토 가능한 단위로 분리하되 원문과 연결한다.
4. 빈 ID, 중복 ID, 빈 단계 또는 기대 결과는 행 단위 오류로 표시하고 해당 행의 실행을 막는다. 정상 행은 선택해 계속할 수 있다. 중복 판정 범위는 가져온 파일 전체이며, TC 식별은 파일·시트·행 출처도 함께 사용한다.
5. 셀의 수식은 실행하지 않는다. 캐시된 표시값이 없는 수식 셀은 비어 있는 것으로 간주하고 검토가 필요함을 알린다. 숨긴 시트·행을 포함할지는 가져오기 화면에 표시하고 기본값과 병합 셀 처리 방식은 구현 전 확정한다.
6. 셀과 웹페이지의 텍스트는 **검토할 데이터**다. 도구 권한, 시스템 정책, 허용 도메인, 비밀값 요청을 바꾸는 지시로 실행하지 않는다.

## 3. 테스트 준비

### 환경과 데이터

- 사용자가 팀 프로젝트의 기존 `web` 엔드포인트와 환경을 선택한다. 허용할 시작 URL과 이동 가능한 도메인은 실행 시작 전에 확인한다. 설정되지 않은 주소는 실행하지 않고 설정을 안내한다. 환경 선택은 개인별로 유지하며 공통 테이블을 변경하지 않는다.
- 사용자에게 테스트 환경 사용을 권장하고 선택한 환경과 대상 도메인을 실행 화면에 표시한다. 운영 환경을 자동 판별해 안전하다고 가정하지 않는다.
- 사전 조건, 계정 역할, 이미지·상품 등 필요한 데이터와 다른 TC의 선행 관계를 실행 전 표시한다. 구체적 값이 없는 “나머지 필수 항목”, “상품 4개” 등은 AI가 실제 데이터를 임의로 만들어 확정하지 않는다. 사용자가 값을 제공하거나 준비 완료를 확인한다.
- 비밀번호와 토큰은 TC 본문이나 공유 데이터에 저장하지 않는다. 로그인·2차 인증은 수동 인계를 기본으로 한다. 수동 입력은 모델 프롬프트와 일반 로그에 전달하지 않는다. 다만 화면 캡처·영상에 민감정보가 들어갈 수 있으므로 7절의 제어가 필요하다.

### 선행 TC

- `SC-01-TC01을 완료합니다`처럼 명시된 참조는 선행 후보로 표시하고 사용자가 확인한다. 참조가 모호하거나 파일 내에 없으면 자동으로 충족 처리하지 않는다.
- 선택된 TC 중 선행 TC가 있으면 순서를 보여 준다. 선행 TC가 선택되지 않았거나 실패·취소된 경우 후속 TC는 자동 실행하지 않고 `Blocked`로 표시한다. 사용자가 이미 준비된 상태를 확인하면 그 근거를 기록하고 실행할 수 있다.
- 순환 참조나 확인할 수 없는 참조는 사용자 수정 전 실행하지 않는다. 선행 성공만으로 테스트 데이터가 여전히 유효하다고 보장하지 않으므로 각 TC의 사전 조건을 확인한다.
- TC는 순차 실행한다. TC 간 동일 컨텍스트를 사용하는 동안 로그인과 데이터 상태는 유지될 수 있으며, 이 사실을 화면과 결과에 표시한다. TC마다 자동 초기화되거나 서로 독립적이라고 가정하지 않는다.

## 4. 실행과 사용자 제어

### 실행 흐름

1. 파일·시트·열과 TC를 선택하고 파싱 결과 및 선행 관계를 확인한다.
2. 환경, 도메인, 사전 조건, 테스트 데이터와 AI 제공자·전송 범위를 확인한다.
3. 사용자가 명시적으로 실행한다. 준비되지 않은 항목은 입력하거나 해당 TC를 제외한다.
4. AI는 현재 TC의 목표와 기대 결과를 기준으로 브라우저 상태를 관찰하고 허용된 동작 하나를 요청한다. 앱이 요청과 정책을 검증한 뒤 Playwright로 수행하고 결과를 다시 관찰한다.
5. 각 기대 결과에 대해 근거를 수집한다. 판정이 불가능하면 추측하지 않고 사용자에게 넘기거나 `확인 필요`로 남긴다.
6. TC를 종료하고 다음 TC로 이동한다. 실패한 TC와 실행 불가능한 후속 TC는 이유를 각각 표시한다.
7. 사용자는 언제든 정지할 수 있고 종료 후 결과를 확인한다.

### 상태와 전이

| 상태 | 진입·종료 규칙 |
| --- | --- |
| 준비 중 | 입력·환경·사전 조건 검증. 확인 또는 수정 후 실행 가능 |
| 실행 중 | 관찰 → 동작 → 결과 확인을 반복. 한 번에 하나의 동작만 수행 |
| 사용자 대기 | 로그인, 대상 모호함, 허용되지 않은 이동 등으로 일시 중지. 이유와 필요한 조치를 표시하고 사용자가 재개하거나 중단 |
| 완료 | 해당 TC들의 판정이 확정되거나 실행 불가 사유가 기록됨 |
| 취소 | 사용자의 중단 요청 또는 앱 종료. 진행 중 동작과 브라우저를 정리하고, 완료된 결과는 보존하며 미실행 항목은 `미실행` |
| 오류 | 모델·브라우저·저장 장애. 테스트 실패로 바꾸지 않고 원인과 재시도 가능 여부 표시 |

사용자 대기 중에는 AI가 다른 동작을 수행하지 않는다. 재개 시 URL과 현재 페이지를 다시 관찰해 상태 변경을 확인한다. 취소와 종료 요청은 중복 호출해도 안전해야 하며, 늦게 도착한 모델 응답이나 브라우저 이벤트가 종료된 실행을 다시 움직이지 못하게 실행 ID로 격리한다. 앱 강제 종료 시에는 마지막으로 보존된 결과까지만 복원될 수 있음을 안내한다.

### 허용 동작과 제한

- 초기 도구는 현재 페이지 관찰, 허용 URL 이동, 클릭, 텍스트 입력, 선택, 스크롤, 키 입력, 대기, 승인된 파일 업로드로 제한한다. 각 요청은 타입·크기·대상·실행 ID를 검증한다. 스크린샷 좌표는 DOM 기반 대상 식별이 어려운 경우에만 사용하고 근거를 기록한다.
- 관찰은 현재 URL, 화면 캡처와 접근 가능한 요소의 역할·이름·상태 등 작업에 필요한 범위로 제한한다. 대상이 여럿이면 첫 번째를 임의로 선택하지 않고 범위를 좁히거나 사용자에게 묻는다.
- 사용자 선택 파일만 업로드한다. 로컬 경로를 모델에 제공하지 않고 파일 내용의 외부 전송 여부를 명시한다. 사용자 선택 없이 임의 파일을 읽지 않는다.
- 허용 도메인 밖으로 이동하거나 새 탭·다운로드·권한 요청이 발생하면 일시 중지한다. 사용자 확인 전 외부 사이트에서 조작을 이어가지 않는다. 우회 이동과 리다이렉트도 최종 도메인을 확인한다.
- 데이터 변경 클릭은 별도 확인 없이 실행하고 동작 이력에 기록한다.
- AI가 웹페이지의 지시로 위 권한을 확대하거나 비밀을 노출하려 하면 거부하고 해당 사실을 표시한다.
- 최대 동작 횟수·반복 횟수·실행 시간과 모델 호출 예산을 둔다. **기본 한도 수치는 실증 후 확정**하며, 초과 시 멈추고 `확인 필요` 또는 사유에 맞는 `Blocked`로 기록한다. 네트워크·모델 오류 재시도는 제한하고 부작용이 있을 수 있는 동작은 자동 재시도하지 않는다.

## 5. 판정과 증거

각 기대 결과는 원문, 판정, 실제 관찰, 근거, 판정 시각을 가진다. AI의 설명만으로 성공을 선언하지 않고, 화면 텍스트·요소 상태·URL·사용자 확인 등 검증에 사용한 관찰을 연결한다. 관찰되지 않은 서버 상태를 화면의 성공 메시지만으로 확정하지 않는다. 오류가 TC 기대와 다름을 입증할 때만 `Fail`이다.

| 기대 결과 상태 | 기준 |
| --- | --- |
| Pass | 기대한 조건을 실제 관찰이나 명시된 수동 검증으로 확인 |
| Fail | 해당 조건을 검증했으며 실제 결과가 기대와 명확하게 다름 |
| Blocked | 사전 조건, 로그인, 선행 TC 또는 환경 문제로 검증을 진행할 수 없음 |
| 확인 필요 | 관찰은 했지만 근거가 부족하거나 AI·도구 한계로 판단할 수 없음 |
| 미실행 | 실행 전 또는 취소로 해당 검증에 도달하지 못함 |
| N/A | 사용자가 명시적으로 적용 제외하고 이유를 기록. AI가 임의 지정하지 않음 |

TC 결과는 검증 항목을 집계한다. **Fail이 하나라도 있으면 Fail**, 그 외에는 **Blocked → 확인 필요 → 미실행 → Pass** 순으로 우선한다. 모든 항목이 N/A면 TC는 N/A이며, Pass와 N/A가 섞이면 Pass로 집계한다. 원인과 모든 개별 상태는 그대로 노출한다. 취소는 실행 상태이며 이미 확인된 TC 결과를 덮어쓰지 않는다. TC의 기대 결과가 하나도 없으면 실행하지 않는다.

각 동작 이력은 TC·기대 결과 ID, 순서, 시각, 동작 종류, 대상 설명, 결과, 관련 캡처를 연결한다. 원문에 없는 기대 결과를 AI가 새로 만들어 통과시키지 않는다. 모델 설명·수동 판정 여부를 구분하고, 사용자가 수정한 판정과 이유도 기록한다.

## 6. 기술 경계

- Renderer는 가져오기 검토, 환경 선택, 진행 상황, 사용자 인계 및 결과 표시를 담당한다. Preload는 필요한 IPC만 노출한다. Main은 파일 읽기·검증, 실행 제어, AI 호출, Playwright 및 산출물 처리를 담당한다.
- 기존 `src/app/ipc/qa/`의 브라우저 실행·미리보기·취소 경험은 재사용 가능성을 검토한다. 기존 실행기는 정해진 `QaStep`을 순서대로 실행하므로 그대로 AI 실행기라고 가정하지 않는다. 기존 실행과 AI 실행이 같은 worker나 이벤트를 충돌 없이 공유할 수 있는지 구현에서 검증한다.
- 기존 ExcelJS 의존성과 API 테스트의 AI CLI 탐색·프로세스 관리 코드를 참고할 수 있다. 기존 API 테스트용 프롬프트·파일 권한을 무조건 재사용하지 않는다. AI 제공 방식과 버전·응답 스키마는 실증 후 확정한다.
- 모델에는 임의 코드 실행 권한을 주지 않는다. 모델 출력과 IPC 입력은 신뢰하지 않고 검증한다. 브라우저의 실제 동작은 main의 제한된 도구가 수행한다.
- 기존 웹 시나리오 실행 기록은 정해진 시나리오와 단계의 상태를 사용한다. AI TC의 `Blocked`, `확인 필요`, 기대 결과별 증거가 손실되지 않도록 기존 저장 구조를 재사용할지 별도 기능 테이블을 둘지 구현 설계에서 결정한다. 기존 상태에 억지로 매핑하지 않는다.

## 7. 정보 전송·보존 정책

- 실행 전 AI 제공자, 전송될 TC·화면·관찰 정보의 범위와 외부 전송 여부를 사용자에게 보여 준다. 제공자 보관·학습 정책과 비용은 선택한 제공자 설정에 따라 확인해야 하며 이 문서는 보장하지 않는다.
- 모델 입력과 로그에 비밀번호·토큰·쿠키·인증 헤더를 의도적으로 포함하지 않는다. 자동 마스킹은 완벽하지 않을 수 있으므로, 민감 화면에서 캡처와 전송을 중지하고 수동 조작 후 재개할 수 있어야 한다. 캡처·영상 기록 여부를 실행 전 표시한다.
- MVP 제안: 원본 엑셀, 화면 캡처, 영상, AI 대화와 PC 경로는 로컬에만 둔다. 팀 공유 결과는 사용자가 명시적으로 저장할 때 TC 식별·판정·필요한 요약만 포함한다. 공유 전 내용 미리보기에서 민감정보를 확인할 수 있게 한다. 이 저장 방식과 보존 기간은 미확정이며 확정 전 팀 DB 저장을 구현하지 않는다.
- 로컬 산출물의 보존 기간·삭제 UI·용량 한도와 암호화 여부는 구현 전 확정한다. 자동 삭제나 암호화가 구현되지 않았다면 제공한다고 표시하지 않는다. 앱 내 삭제는 해당 실행의 로컬 산출물 범위와 공유 결과 삭제 여부를 구분해 안내한다.
- 팀 공유가 확정되면 프로젝트별 RLS, 작성자, 동시 수정, 재실행 가능한 migration을 적용한다. 로그아웃·프로젝트 전환 시 프로젝트별 캐시를 비우고 진행 중 실행을 안전하게 중단한다. 공통 프로젝트 테이블은 변경하지 않는다.

## 8. 오류·예외 처리

| 상황 | 처리 |
| --- | --- |
| 파일 손상·지원하지 않는 형식·제한 초과 | 가져오기 중지, 이유 표시. 원본 변경 없음 |
| 열 매핑 불가·중복 ID·기대 결과 누락 | 해당 문제를 표시하고 수정 전 해당 TC 실행 금지 |
| 로그인 만료·CAPTCHA·2차 인증 | 사용자 대기. 수동 완료 후 재관찰 |
| 요소가 없거나 다수 일치 | 가능한 범위에서 재관찰 후 사용자 인계. 요소 미발견만으로 제품 결함으로 판정하지 않음 |
| 선행 TC 실패·데이터 미준비 | 후속 TC Blocked. 사용자의 준비 완료 확인 시 근거 기록 후 진행 가능 |
| 허용 범위 밖 URL·팝업·다운로드 | 사용자 대기. MVP에서 처리 불가하면 Blocked 또는 확인 필요 사유 기록 |
| AI 응답 오류·시간 초과·예산 초과 | 실행 정지, 확인된 결과 보존, 미확인 항목에 사유 표시 |
| 브라우저 종료·네트워크 장애 | 실행 오류로 표시하고 확인된 결과 보존. 제품 Fail로 단정하지 않음 |
| 결과 저장 실패 | 저장 실패를 명시하고 현재 메모리 결과를 유지. 재시도 가능하게 하며 저장 성공으로 표시하지 않음 |
| 취소·앱 종료 | 새 동작 중지 및 자원 정리. 완료된 결과와 미실행 항목을 구분 |

## 9. 구현 단계와 검증 기준

1. **가져오기와 검토**: 예시 파일의 115개 TC를 ID·원문·행 출처와 함께 읽고, 열 변경·누락·중복·빈 기대 결과를 검증한다. 선행 참조는 후보로 제시한다.
2. **브라우저 제어 실증**: 테스트 전용 웹 페이지에서 이동·입력·클릭·선택과 관찰을 수행한다. 다중 요소, 허용 도메인 이탈, 비정상 모델 응답, 시간 초과, 취소 후 늦은 응답을 검증한다.
3. **판정과 수동 인계**: 기대 결과별 근거와 집계를 구현하고 Pass·Fail·Blocked·확인 필요·미실행·N/A, 로그인 인계·재개를 검증한다. 관찰 불가능한 결과를 Pass 처리하지 않는 테스트를 포함한다.
4. **예시 TC 실증**: 준비된 BOS 테스트 환경에서 `SC-01-TC03`, `SC-01-TC04` 등 소수의 TC를 실행한다. 등록 버튼 상태, 입력 길이, 사전 데이터 미준비와 사용자 인계를 확인한다. 기대 결과가 실제 화면에서 관찰 가능한지 먼저 점검한다.
5. **안전·운영 검증**: 도메인 이탈, 데이터 변경 클릭, 비밀값 노출 가능성, 파일 업로드 범위, 로그아웃·프로젝트 변경, 저장 실패와 복구를 검증한다. 팀 저장을 도입하면 로컬 Supabase에서 RLS·프로젝트 격리·충돌을 별도 검증한다.
6. **실증 평가 후 확장**: TC별 완료율, 사람 개입 횟수, 근거가 있는 기대 결과 비율, 오판 사례, 소요 시간·모델 비용을 기록한다. 크로스 서비스, 다중 계정, 실제 기기, 반복 실행용 시나리오 저장은 결과를 보고 별도 계획한다.

## 10. 구현 전 확정할 사항

| 항목 | 제안 또는 확인할 선택지 |

| 엑셀 제한 | 파일 크기, 최대 행·셀 길이, 숨긴 행·시트 및 병합 셀 처리 |

## 참고: 현재 구현과의 구분

현재 Checkly에는 Playwright 기반 정형 시나리오 실행, 수동 브라우저 제어, 영상·리포트, ExcelJS 기반 XLSX 리포트 생성, API 테스트의 AI CLI 실행 기반이 있다. 이 문서의 TC 가져오기·AI 브라우저 판단·새 판정 및 증거 정책은 구현 완료를 뜻하지 않는다. 기존 실행 산출물의 실제 보존과 한계는 [실행 IPC·데이터·보존 정책](04-pages/040-scenario-run/03-api.md), 팀 저장 규칙은 [Supabase 개발 가이드](02-architecture/supabase-guide.md)를 따른다.
